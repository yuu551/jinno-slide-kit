# 話の組み立てとリード

神野さんの資料で再現するのは、具体例と図の関係。特定の題材や枚数、発表者の経歴は別の資料へ持ち込まない。

## 書き始める前に決める3つ

1. 一つの具体例。全ページでこの例を使い回す。たとえば「夜間集計の3件のうち在庫だけが失敗した」「問い合わせ対応のAgentが注文APIを2回呼んで遅い」。対象のID・値・役割も最後まで同じものを使う。例がないと図が機能名の箱の並びになり、AIが作った資料に見える。
2. 聴き手と、読み終えたら何ができるか。アップデート紹介なら「自分の構成で何が楽になり、何を設定すればよいか」が分かること。
3. 冒頭で置く問いと、その答えを出すページ。冒頭で取り上げた問いには資料の中で答える。

## ページごとに役割を変える

全ページを「タイトル＋2行のリード＋図」で同じ密度にしない。役割で情報の出し方を変える。

| 役割 | 出し方 | 作例の見本 |
|---|---|---|
| 場面を作る | 人とAgentとサービスの線画、依頼の吹き出し | CIMD p.6、RAG p.8、Jev p.4 |
| 判断を示す | 一つの結論、大きな対比、止める位置を強調した図 | CIMD p.28、Jev p.21 |
| 仕組みを説明する | 構成図・経路・時系列 | CIMD p.25・36、RAG p.48 |
| 実装に落とす | 設定例・コード・値の表 | CIMD p.38、Jev p.12・13 |
| 条件を確かめる | 拒否の例・制約・失敗時の分岐 | CIMD p.47、Jev p.32 |
| 間を作る | 人とAgentの短い会話、問いかけ | Jev p.9・15、RAG p.11・20 |
| 締める | 次の一歩を図で示す | CIMD p.54、RAG p.79・80 |

この順を毎回の決まった並びにしない。足りない役割だけを補い、似た画面が続く所を変える。間を作るページにも問い・判断・発見を置く。空白や大きな絵だけで緩急を作らない。

## タイトル・リード・図の分担

3段が同じ話を3回言わないようにする。

| 層 | 役割 | 例 |
|---|---|---|
| タイトル | 何の話か。読点を入れない | 失敗した集計だけを再実行する |
| リード | そのページで伝える動作・判断・制約。誰が何をするかを先に書く | 例「入口で利用者のJWTを検証し、接続先へは実行ロールでアクセスします」 |
| 図・表・コード | 根拠と手順を見せる | 役者・経路・値の例・止める位置 |

- リードは1〜2文。背景 → 今の問題 → このページの判断がつながるなら2文にする。1文で済むなら1文。
- 1文に主語の「が」を2つ重ねない。NG「結果がキャッシュにない要求がAPIへ送られます」→「キャッシュに結果がない要求だけをAPIへ送ります」のように係り方を1つにするか、文を分ける。
- 抽象的なリードを具体にする。NG「安全なアクセス制御を実現します」→「JWTのsubとactorIdが違う要求は、検索の手前で止めます」。NG「以下に接続方式を整理しました」→「ツールをまとめて探したいか、独立したサーバーへ直接つなぐかで選びます」。
- 機能名を説明の入口にしない。用途と動作をリードで書いてから正式名を対応づける。正式名は消さない（読者が調べるときに要る）。
- タイトルとリードにびっくりマークや装飾のコロンを使わない。会話では自然な感嘆符を使ってよい。
- 主語や目的語を落とした短句（「注文APIはもう動いている」「注文・在庫・配送。ツールが増えてきた」）を作者らしさと取り違えない。何をしたいかを書く。
- 図の中にリードの言い直しや、まとめの一文を書かない。図の上端に帯を置かない（タイトルが二重になる）。

## 会話と疑問

会話は機能説明を2人に読ませるためのものではない。前の説明を受け止めて、分からない言葉や次の疑問を聞く。次のページで本当にその疑問に答える。人は左、Agentは右（`::: dialogue`）。

| 疑問の型 | 会話の例 | 次のページが答えること |
|---|---|---|
| 多すぎて戸惑う | 私「できることは分かったよ。これ全部要るの？」 | 最小の構成と、足す条件 |
| 便利さを疑う | 私「直接つながるのに、間に入れると複雑にならない？」 | 直接つなぐ場合との比較、要る条件 |
| 分かったから次の心配へ | 私「まとめて使えるんだね。誰でも全部使っていいの？」 | 誰に何を許可するか |
| 自分でできるか不安 | 私「例は分かったけど、自分の構成は何から決めよう？」 | 判断の順番と最初の一歩 |

発話の頭を毎回「なるほど」にしない。Agentの返事は答えの要点を一つ渡す（「今から説明します」だけで終えない）。会話の内容をリードでくり返さない。架空の検証ログや発表者の体験談に見せない。

図の中の吹き出しも同じ考え方で書く。人の吹き出しには具体的な依頼や疑問（「注文1042は今どこ？」「返金は人が承認したい」）、サービスの吹き出しには条件（「読み取り専用のロールで呼ぶ」）。

## 濃さは具体的な入出力で作る

濃いページとは、文字が多いページではなく「何がどこに入り、何を渡し、どう返るか」が見えるページ。

- 設定値が何に属するかを枠の階層で示す。設定欄と実際の接続先は分ける。
- 矢印に要求・応答の意味を付け、名前や値の例を近くに置く。代表の1例を追える量に絞る。
- 想定の出力には「例」と書く。実行していない結果を実測に見せない。
- 同じ話題の「概要」「設定」「注意点」が薄く分かれていたら1ページに組み直す。読めなくなるなら文字を縮めずにページを分ける。
- 表の列を箱に変えただけでは関係の説明は増えない。項目を横断して読むなら表、登録先・受け渡す値・処理の順・分岐を追う話なら図。

## 通して読む

`slides notes <slides.md>` でタイトルとリードだけを続けて読む。次を確認する。

- 今のページが、直前に生まれた疑問に答えているか。
- 読者が知らない用語・登場人物・操作が突然増えていないか。初出で用途を説明しているか。
- 情報の多いページの間に、要点を整理するページがあるか。会話・結論・構成図・コード・表に変化があるか。
- 冒頭の問いと具体例に最後に戻り、何ができるようになったかが分かるか。
- 語尾の「す。」だけが次の行に落ちていないか。読点が続いていないか。

単に「図を増やした」「文字を増やした」を完成の条件にしない。
